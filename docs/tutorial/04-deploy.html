Deploy to Streamlit-in-Snowflake

Three ways to deploy — push, pull, or workspace. Understand when to use each, then create your first versioned release.

Deploy: workspace-native approach

💡
Three deploy mechanisms — when to use each:
Mechanism Best for Command
A. snow CLI push CI/CD + multi-object deploys (tables, RBAC) make deploy
B. GIT REPOSITORY pull Rapid iteration from Snowsight (no CI) make deploy-git
C. Workspaces Interactive dev, pairing, non-CLI users Snowsight → Deploy button
This repo supports all three. The CI pipeline uses A (push); developers choose B or C for inner-loop iteration.

Option A — CLI (scripts/30_deploy.sh)

snow streamlit deploy reads app/snowflake.yml for the compute pool, runtime, and EAI settings, then uploads your local app/ files to a Snowflake stage and creates/replaces the STREAMLIT object.

bash — after scripts/10_setup.sh
scripts/30_deploy.sh -c oregon-sedemo
# Equivalent to:
snow streamlit deploy -c oregon-sedemo -p app/ --replace

Option B — Snowsight Workspace

  1. Open Snowsight → Workspaces → New workspace
  2. Browse to app/streamlit_app.py and press Run for a private dev preview
  3. Press Deploy — Snowsight reads app/snowflake.yml for settings
💡
Both options deploy the same STREAMLIT object in the same database/schema. CI/CD uses Option A (30_deploy.sh). Interactive development can use either — the workspace provides a live preview before publishing.

app/snowflake.yml

The snowflake.yml in the app/ directory declares all deployment settings. Both the workspace Deploy button and snow streamlit deploy read it. Environment overrides via ctx.env let the same file deploy to dev, PR previews, and production — no config drift across branches.

app/snowflake.yml (parameterised)
definition_version: 2
entities:
  ingest_console:
    type: streamlit
    identifier:
      name: <% ctx.env.GIT_SIS_APP_NAME | default('INGEST_CONSOLE') %>
      schema: <% ctx.env.GIT_SIS_SCHEMA | default('GIT_SIS') %>
      database: <% ctx.env.GIT_SIS_DATABASE | default('SNOWFLAKE_LEARNING_DB') %>
    title: "Ingestion Ops Console"
    query_warehouse: <% ctx.env.GIT_SIS_WAREHOUSE | default('COMPUTE_WH') %>
    compute_pool: SYSTEM_COMPUTE_POOL_CPU
    runtime_name: SYSTEM$ST_CONTAINER_RUNTIME_PY3_11
    main_file: streamlit_app.py
    external_access_integrations:
      - PYPI_ACCESS_INTEGRATION
    artifacts:
      - streamlit_app.py
      - pyproject.toml
      - .streamlit/config.toml
      - pages/1_run_history.py
      - pages/2_error_explorer.py
      - lib/__init__.py
      - lib/config.py
      - lib/ingest.py
      - lib/session.py
      - lib/components/__init__.py
      - lib/components/metrics.py
💡
Why ctx.env parameterisation?
One artifact deploys everywhere: make deploy (prod), GIT_SIS_SCHEMA=GIT_SIS_PR_42 make deploy (PR preview), make deploy CONN=prod-conn GIT_SIS_DATABASE=PROD_DB (production). No config-by-branch drift, no copy-paste errors.

Versioned releases + instant rollback

Every deploy creates a version alias you can roll back to instantly — no redeploy needed:

Automatic: MAIN_<sha> on every main-branch deploy

Each time CI deploys to main, it commits a MAIN_<7-char-sha> alias (e.g. MAIN_A1B2C3D). Roll back to any prior deploy:

SQL — rollback to a prior main-branch deploy
-- List available versions:
SHOW VERSIONS IN STREAMLIT SNOWFLAKE_LEARNING_DB.GIT_SIS.INGEST_CONSOLE;

-- Instantly roll back to any prior deploy:
ALTER STREAMLIT SNOWFLAKE_LEARNING_DB.GIT_SIS.INGEST_CONSOLE
  SET DEFAULT_VERSION = MAIN_A1B2C3D;   -- first 7 chars of target commit SHA

Manual: tag a semver release

Push a vX.Y.Z tag to commit an immutable, named version:

bash — cut a versioned release
git tag v1.0.0
git push origin v1.0.0
# → release.yml: deploys + COMMIT VERSION V1_0_0 (sanitized)
SQL — rollback to a semver release
ALTER STREAMLIT SNOWFLAKE_LEARNING_DB.GIT_SIS.INGEST_CONSOLE
  SET DEFAULT_VERSION = V0_9_0;  -- prior good version from SHOW VERSIONS
💡
See docs/runbook.md for the full release/rollback procedure. Both MAIN_<sha> (every CI deploy) and V1_2_3 (tagged releases) appear in SHOW VERSIONS.

GitOps pull-based deploy (advanced)

Once make setup-git has been run and the GitHub App authorized in Snowsight, you can use the pull-based GitOps deploy workflow: Snowflake fetches directly from GitHub rather than receiving uploaded files. Every deployed version is traceable to a specific git commit SHA.

bash — trigger pull-based deploy
# In GitHub: Actions → "Deploy (GitOps / pull-based)" → Run workflow
# Choose environment (ci / prod) and branch (default: main)
# The workflow:
#   1. ALTER GIT REPOSITORY APP_REPO FETCH
#   2. ALTER STREAMLIT ADD VERSION MAIN_<sha> FROM @APP_REPO/branches/main/
#   3. ALTER STREAMLIT SET DEFAULT_VERSION = MAIN_<sha>

# Or manually via make (updates LIVE version from current branch tip):
make deploy-git
💡
Push vs pull: push-based (make deploy) works immediately without git wiring, and is what CI uses by default. Pull-based gives full SHA traceability. See docs/WAYS-OF-WORKING.md §3 for the decision guide.

Teardown (cleanup)

Two cleanup levels — choose based on what you want to preserve:

🔄

90_cleanup.sh — reset demo

Drops GIT_SIS schema, STREAMLIT, GIT REPOSITORY, and API integration. Rebuild with 10_setup.sh && 30_deploy.sh.

☢️

99_cleanup-infra.sh — full teardown

Drops everything. Prompts for confirmation. Use --yes to skip. Only for complete decommissioning.

bash — normal reset
scripts/90_cleanup.sh -c oregon-sedemo
bash — full decommission
scripts/99_cleanup-infra.sh -c oregon-sedemo
# or without confirmation prompt:
scripts/99_cleanup-infra.sh -c oregon-sedemo --yes
